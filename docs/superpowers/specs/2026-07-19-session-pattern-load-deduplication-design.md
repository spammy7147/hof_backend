# 세션 패턴 로드 중복 제거 설계

## 목표

같은 HOF 계정과 로그인 세션에서 이미 로드된 캐릭터 패턴을 다음 전투가 그대로 요구하면 패턴 로드 요청을 생략하고 전투를 바로 실행한다. 자동전투와 전투 탭의 수동전투가 동일한 규칙을 사용한다.

## 현재 동작

모든 `RunBattleRequest`는 파티 캐릭터별 `patternLoads`를 포함한다. `BattleRunService`는 전투마다 이 목록 전체를 HOF에 순서대로 로드한 뒤 전투를 요청한다. 따라서 A맵과 B맵이 같은 프리셋을 사용해도 B맵 전에 같은 패턴을 다시 로드한다.

## 선택한 접근

백엔드 프로세스에 계정·HOF 세션별 패턴 상태를 추적하는 공통 컴포넌트를 둔다. 외부 HOF 상태를 영속 데이터로 간주하지 않기 위해 DB에는 저장하지 않는다. 서버 재시작 뒤 첫 전투는 전체 패턴을 다시 로드하는 보수적인 동작을 한다.

클라이언트나 자동화 실행부에서 이전 프리셋을 비교하지 않는다. 두 실행 경로 모두 이미 `BattleRunService`에 모이므로 중복 제거도 이 공통 경계에서 수행한다.

## 패턴 동일성

캐시는 프리셋 ID나 캐릭터 ID만 비교하지 않는다. 각 캐릭터의 현재 로드 상태를 `(hofCharacterId, patternSlot)`로 판단한다.

- 같은 캐릭터와 같은 슬롯이면 로드를 생략한다.
- 같은 캐릭터라도 슬롯이 달라지면 해당 캐릭터만 다시 로드한다.
- 파티 순서나 맵 코드는 패턴 동일성에 영향을 주지 않는다.
- 다른 계정의 상태는 공유하지 않는다.

## 세션 경계

추적기는 쿠키 이름과 값을 정규 순서로 해시한 세션 지문을 사용한다. 원본 쿠키 값이나 지문은 로그에 남기지 않는다.

- 같은 계정이라도 세션 지문이 달라지면 기존 패턴 상태를 폐기한다.
- 빈 쿠키는 기존 `HOF_SESSION_EXPIRED` 처리에 맡기며 캐시 판단에 사용하지 않는다.
- 서버 재시작으로 메모리 상태가 사라지면 다음 전투에서 전체 패턴을 다시 로드한다.
- 자동화의 세션 복구가 새 쿠키를 저장한 뒤 전투를 재시도하면 새 지문이 감지되어 전체 패턴을 다시 로드한다.

## 구성 요소

### 세션 패턴 추적기

새 Spring singleton 컴포넌트가 다음 책임을 가진다.

- 계정별 실행 잠금 제공
- 현재 쿠키 세션 지문과 캐릭터별 마지막 슬롯 보관
- 요청한 `patternLoads` 중 현재 상태와 다른 항목 계산
- 성공한 패턴 로드만 현재 상태에 반영

상태는 계정별로 제한되고 캐릭터당 슬롯 하나만 보관한다. 별도 TTL이나 영속화는 도입하지 않는다.

### `BattleRunService`

캐릭터 검증을 마친 뒤 계정별 잠금 안에서 다음 순서를 수행한다.

1. 현재 쿠키로 세션 상태를 선택하거나 초기화한다.
2. 요청한 패턴 중 필요한 항목만 계산한다.
3. 필요한 패턴을 기존 순서대로 로드한다.
4. 활성 세션이고 HTTP 상태가 성공 범위인 항목만 추적기에 반영한다.
5. 같은 잠금을 유지한 채 전투를 제출하고 결과를 처리한다.

잠금이 패턴 로드부터 전투 제출까지 이어지므로 같은 프로세스의 수동전투와 자동전투가 서로 다른 패턴을 중간에 끼워 넣지 못한다.

### `CharacterPatternService`

캐릭터 화면에서 사용자가 명시적으로 누른 패턴 로드는 생략하지 않는다. 사용자 요청대로 HOF에 로드하고 성공한 `(characterId, slot)`을 같은 추적기에 기록한다. 이 작업도 같은 계정별 잠금을 사용하여 진행 중인 전투와 섞이지 않게 한다.

## 실패 처리

- 패턴 로드 중 로그인 만료가 감지되면 기존 예외를 유지하고 해당 항목을 캐시에 기록하지 않는다.
- 성공 범위가 아닌 HTTP 응답은 캐시에 기록하지 않는다. 기존 전투 처리 의미는 이번 변경에서 확대하지 않는다.
- 일부 패턴만 성공한 뒤 실패하면 성공이 확인된 항목만 남는다. 다음 요청은 미확인 항목을 다시 로드한다.
- 전투 자체가 실패해도 이미 성공한 패턴 로드는 HOF 세션에 반영된 사실이므로 추적 상태를 유지한다.

## 동시성과 배포 한계

계정별 잠금은 현재 백엔드 프로세스 안의 호출을 직렬화한다. 프로세스가 여러 개라면 각 프로세스는 독립 캐시를 가지므로 중복 로드가 추가로 발생할 수 있지만, 첫 요청에서 보수적으로 다시 로드한다.

여러 프로세스가 같은 HOF 계정에 동시에 서로 다른 패턴을 로드하는 문제를 완전히 막으려면 모든 수동·자동 HOF 변경 요청을 아우르는 분산 계정 lease가 필요하다. 이는 이번 중복 제거 범위에 포함하지 않는다.

## 검증

- 첫 전투는 요청한 패턴 전체를 로드한 뒤 전투한다.
- 같은 계정·세션·패턴으로 다른 맵을 이어서 실행하면 두 번째 전투는 패턴을 로드하지 않는다.
- 캐릭터 하나의 슬롯만 바뀌면 그 캐릭터 패턴만 다시 로드한다.
- 세션 쿠키가 바뀌면 같은 프리셋도 전체 패턴을 다시 로드한다.
- 계정이 다르면 같은 캐릭터·슬롯 정보도 공유하지 않는다.
- 캐릭터 화면의 직접 패턴 로드 성공이 다음 전투의 중복 판단에 반영된다.
- 자동전투가 만드는 기존 `RunBattleRequest` 계약은 변경하지 않는다.
- 관련 단위 테스트와 전체 백엔드 테스트를 통과해야 한다.

## 제외 범위

- 앱 API DTO 변경
- 프리셋 저장 구조 변경
- DB 마이그레이션
- 여러 백엔드 인스턴스 사이의 분산 캐시 또는 분산 잠금
- HOF 웹사이트를 앱 밖에서 직접 조작한 상태 감지
